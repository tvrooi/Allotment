# FinX comparison: FlyBudget gaps and implementation candidates

Investigation date: 28 October 2026. FlyBudget source baseline: `297497bf18b77c399ebc38142fb92d153e3348ce` (`0.2.0-up.48`, `SRC`).
FinX source baseline: `9c89557928fa1fdc8a30028ae21eea48d2f790f7` (`FINX`, shallow clone of `IT-BAER/finx`, changelog head v1.5.0, 9 October 2026).
This is a proposed backlog, not authorization to implement it. Nothing was run: neither app was started, FinX's dependencies were not installed and none of its scripts were executed. No FlyBudget or FinX file was modified. Line references describe `SRC` and `FINX`; follow-up changes must recheck them.

Written to the format of the [Actual comparison](actual-flybudget-gaps.md) (`ACT-*`) and the [YNAB gap report](ynab-flybudget-budget-gaps.md) (`BUD-*`); shared gaps cite those IDs. The [Securo comparison](securo-flybudget-gaps.md) (`SEC-*`) found the missing web app manifest independently as `SEC-06`.

- **The Android app could not be read.** `FINX android/` is an empty directory in the clone (no `.gitmodules`, no files). Everything said about the native app comes from FinX's own README (lines 347-356), CHANGELOG and `docs/privacy_policy_android.md`, plus the server endpoints the app calls. Native behaviour (widgets, notification listener, biometric flow, local database, background fetch) is therefore **unverified at source level**. No claim about FinX widgets is made: the only "widget" strings in the repo are server comments about a dashboard card.
- **FlyBudget read:** the schedule, notify, gateway, receipt, offline outbox, auth, MCP, household and forecast code named below, the phone, offline, importing, recurring, reports and dashboard user guides, and `docs/HOUSEHOLDS.md`, `MULTI-USER-PLAN.md`, `READ-ONLY-ACCESS.md`, `RECEIPTS-AND-TAX.md`.

- FinX is source-available (Apache-2.0 with Commons Clause). This report describes behaviour and cites paths; no FinX code should be copied into the AGPL fork without a licence check.

## What FinX is

A transaction tracker, not an envelope budget: a flat `transactions` table (`amount NUMERIC(10,2)`, `type income|expense`, [FINX database/init.sql#L102](https://github.com/IT-BAER/finx/blob/9c89557/database/init.sql#L102)), category/source/target lookup tables, a single optional monthly `budget_limit` per category (migration 014), standalone savings goals that are never linked to money in accounts (migration 009), recurring rules, user-to-user sharing, Zod-validated Express routes, and a React 19 + Tailwind 4 + TanStack Query web app. Its distinctive pieces are the native Android app (Local Mode, biometric, notification parsing), an optional OpenRouter-backed AI layer (receipt OCR, notification parsing, speech parsing, a tool-calling chat), SSE live updates, and cross-user transaction mirroring. It has no envelope accounting, no Ready to Assign, no reconciliation, no transfers as a first-class type, no splits, no payees, no rules engine beyond a per-merchant category memory, no investments or forecasting, and one currency per UI language.

So the overlap with FlyBudget is narrow, and most of FinX is behind FlyBudget. The gaps below are the places where FinX's approach is better or where it exposed a FlyBudget shortcoming.

## Priority and verification conventions

- **P1:** correctness, data-loss or security risk, or a gap that misleads money decisions. No P1 gap was found against FinX.
- **P2:** meaningful workflow gap.
- **P3:** nice to have, or a decision to record rather than a defect.
- **C / S(file) / E(file):** as in the YNAB report. Proposed checks only; none were run.

## P2 · FINX-01: schedule occurrences and auto-create run only at server start

- **FinX:** a daily recurring job registered at boot, first run at 02:00, then every 24 hours ([server.js#L236](https://github.com/IT-BAER/finx/blob/9c89557/server.js#L236)), through a small interval scheduler ([services/scheduler.js#L53](https://github.com/IT-BAER/finx/blob/9c89557/services/scheduler.js#L53)). A manual admin trigger exists (`routes/recurring-tools.js`).
  The job itself is weak (see "Where FlyBudget leads"), but it runs without a restart.
- **FlyBudget today:** [`ensureOccurrencesForAll`](../../server/src/index.ts#L252) (90 days ahead) and [`autoCreateDueScheduled`](../../server/src/index.ts#L286) are called once, from `runStartupTasks`, after the bank sync. The only other caller of auto-create is `POST /api/schedules/auto-create` ([routes](../../server/src/routes/schedules.ts#L272)), which nothing in `client/src` calls. The only repeating timers in the server are the session cleanup, the exchange-rate fetch and [Up polling](../../server/src/services/upSyncService.ts#L271).
  The user guide states the limit for auto-create ("when FlyBudget starts on or after that day", [recurring.mdx](../../website/docs/recurring.mdx#L28)); it does not mention the 90-day occurrence horizon, which is only extended at start ([`occurrenceHorizon`](../../server/src/services/scheduleService.ts#L17)).
- **Why it matters here:** the owner's server is a Home Assistant app that runs for weeks. A payday or bill set to auto-create is posted only when the app next restarts. Stored occurrences are what bank transactions are matched against ([matchingEngine.ts](../../server/src/services/matchingEngine.ts)) and what the recurring page and review use for paid/upcoming status, so a server left up past its horizon stops producing them.
  The cash forecast is not affected: [it computes occurrences itself](../../server/src/services/forecastService.ts#L172) as well as reading stored ones. Frequent releases restart the app and probably hide this; that is a guess, not a measurement.
- **Seam:** a `setInterval` (hourly, `.unref()`) next to Up polling that calls `ensureOccurrencesForAll`, then `autoCreateDueScheduled`, after the latest bank sync, reusing `runStartupTask` error isolation. Keep the existing ordering rule (sync first, so real transactions match before anything is created) and the `schedule:<id>:<occ>` imported ids, which make a second run harmless.
- **Invariants:** idempotent (the imported id already guarantees one transaction per occurrence); never create before `autoCreateFrom`; a failing run is logged and does not stop the timer. Not run in multi-user mode twice: each budget process owns its own timer.
- **Acceptance:** with a fake clock, a schedule due tomorrow is created after the timer crosses midnight with no restart; a second tick creates nothing; an occurrence 91 days past the last start exists after a tick.
- **Smallest checks:** S(a new `scheduleTimer.test.ts`), `cd server && npx tsc --noEmit`. Escalate to P1 if the matching or paid-status gap past the horizon is reproduced.

## P2 · FINX-02: bill and payday reminders

- **FinX:** `recurring_transactions.reminder_enabled` and `reminder_lead` (`day|week|month`) are stored per rule ([migration 017](https://github.com/IT-BAER/finx/blob/9c89557/database/migrations/017-add-recurring-reminder-fields.sql), CHANGELOG v1.2.1), and the Android app turns them into renewal notifications (the native side is not in the clone). A server endpoint feeds an upcoming-bills card ([recurring-transactions.js#L14](https://github.com/IT-BAER/finx/blob/9c89557/routes/recurring-transactions.js#L14)). FinX removed server push in v0.8.7 (CHANGELOG line 214) and relies on the app.
- **FlyBudget today:** nothing sends a reminder. [`UpcomingBills`](../../client/src/components/dashboard/UpcomingBills.tsx) and the recurring page show what is due when someone opens them. The only outbound notification code is the gateway's Home Assistant `notify` call, used for password reset codes ([notify.ts#L12-L35](../../server/src/gateway/notify.ts#L12)). `resilienceService` has a "resume reminder" that is an on-screen state, not a message. `grep -i remind` over server and client finds no bill reminder.
- **Why it matters here:** the owner runs Home Assistant, so a phone notification needs no new infrastructure. This is the cheapest way to make the web-only phone story (no native app) feel finished, and it turns the schedule data into action on due dates.
- **Seam:** a per-schedule lead (additive column on `schedules`) plus a settings choice of notify service; send from the FINX-01 timer. The Supervisor token should reach the single budget (`homeassistant_api: true`, [config.yaml#L26](../../homeassistant/config.yaml#L26); [ha-launch.cjs#L56](../../homeassistant/ha-launch.cjs#L56) copies settings into `process.env` without removing it; not tested) but is **deliberately deleted from each child budget in multi-user mode** ([budgets.ts#L146-L147](../../server/src/gateway/budgets.ts#L146)), so in that mode a budget would ask the gateway to send, as the password codes do. Reuse `NOTIFY_SERVICE` validation.
- **Invariants:** off by default; message text is generic (no amounts or payee names unless the owner opts in, since notification previews show on lock screens); at most one message per occurrence; nothing leaves Home Assistant. Not available outside Home Assistant (`canNotify()` false): the settings control says so.
- **Acceptance:** an occurrence three days out with lead `day` sends one notification the day before; a second tick sends none; a paid occurrence sends none; in multi-user mode only the owning person's service is called.
- **Smallest checks:** S(a new reminder test with a stub `Notify`), `ha-launch` tests unchanged; C for the settings control.

## P2 · FINX-03: phone shell (installability and one-tap add)

Same installability gap as [SEC-06](securo-flybudget-gaps.md#p2--sec-06-no-web-app-manifest).

- **FinX:** `index.html` carries `viewport-fit=cover`, `theme-color`, and two `apple-touch-icon` links ([frontend/index.html#L21-L77](https://github.com/IT-BAER/finx/blob/9c89557/frontend/index.html#L21)), and `public/offline.html` is an offline landing page. A bottom bar on phones has a raised floating action button that opens add-transaction from any page ([Navbar.jsx#L523-L545](https://github.com/IT-BAER/finx/blob/9c89557/frontend/src/components/Navbar.jsx#L523)). `SwipeableRoutesInner.jsx` swaps the four main pages by swipe and `utils/haptics.js` vibrates on taps. FinX itself ships **no** web manifest (`frontend/public` holds icons, logos, `offline.html`, `sitemap.xml`), relying on the native app for installation.
- **FlyBudget today:** [`client/index.html`](../../client/index.html) has no manifest link, no `apple-touch-icon`, no `theme-color` and no `viewport-fit=cover`; there is no manifest file in `client/public` (`logo.png`, `sw.js` only). The service worker caches the app shell ([sw.js](../../client/public/sw.js)) but a worker alone does not make the page installable. The guide says "Add to Home Screen... FlyBudget then opens like an app" ([phone.mdx#L33-L37](../../website/docs/phone.mdx#L33)). `env(safe-area-inset-*)` is used in sheets ([Modal.tsx#L80](../../client/src/components/ui/Modal.tsx#L80)) but without `viewport-fit=cover` those insets are zero on notched iPhones.
  On phones the shell is a top bar and a drawer ([AppShell.tsx#L96-L121](../../client/src/components/layout/AppShell.tsx#L96)). Adding a transaction is a button on the Transactions page and account pages ([Transactions.tsx#L72](../../client/src/pages/Transactions.tsx#L72)); from the budget it takes the drawer, then Transactions, then Add. A `?add=1` link already opens the dialog ([useOpenFromLink.ts](../../client/src/hooks/useOpenFromLink.ts#L9)).
- **Why it matters here:** the brief's biggest FlyBudget shortfall is no native mobile app. Whether Chrome offers a real install and whether iOS opens the shortcut standalone without a manifest depends on browser versions and was not tested; the documented behaviour is at best browser-dependent. Cheap metadata closes most of the visible distance to a native app, and one-tap add is the action a phone gets used for.
- **Seam:** `client/public/manifest.webmanifest` (name, `display: standalone`, icons incl. maskable, `theme_color`, `start_url`, a `shortcuts` entry pointing at `/transactions?add=1`), link tags in `client/index.html`, `viewport-fit=cover`, and a phone-only add button in `AppShell` (not on desktop; the sidebar already has room). The server's security headers ([middleware/security.ts](../../server/src/middleware/security.ts)) and the desktop app's `flybudget-mac-window` marker need rechecking for the manifest request. Related: [BUD-04](ynab-flybudget-budget-gaps.md) (phone budget layout).
- **Invariants:** no service-worker change to API caching (`/api` never cached); desktop/Electron untouched; the page must still work signed out (login page uses the same shell).
- **Acceptance:** manifest validates in the browser's installability audit; the add button appears at phone width on every route, opens the same dialog, and does not cover the budget amount sheet; `e2e/tests/phone/` passes with the button present.
- **Smallest checks:** C; E(`phone/phone.spec.ts`, `phone/overflow.ts`); manual install check on one Android and one iPhone (not done here).

## P3 · FINX-04: make a transaction recurring from its own form

- **FinX:** the add and edit forms have a "Make recurring" switch with interval, end date and occurrence limit, and a preview ([AddTransaction.jsx#L555-L575](https://github.com/IT-BAER/finx/blob/9c89557/frontend/src/pages/AddTransaction.jsx#L555), strings `makeRecurring`, `recurringTransactionPreview`).
- **FlyBudget today:** schedules are created only on the Recurring page: `useCreateSchedule` has one caller ([RecurringTransactions.tsx#L44](../../client/src/pages/RecurringTransactions.tsx#L44)). A transaction row can show and unlink its schedule ([TransactionDetailPanel.tsx#L398](../../client/src/components/transactions/TransactionDetailPanel.tsx#L398)), and **Find recurring** discovers repeats after the fact, but there is no "Repeat this" on a transaction.
- **Why it matters:** the commonest moment to realise a payment repeats is when entering or reviewing it.
- **Seam:** a detail-panel action that opens the existing schedule dialog prefilled from the transaction (payee, account, category, amount, date as start) and links that transaction as the first paid occurrence via the same path Find recurring uses ([scheduleDiscovery.ts#L524](../../server/src/services/scheduleDiscovery.ts#L524)).
- **Invariants:** no duplicate transaction is created; transfers, split parents and reconciled rows follow the same eligibility as discovery.
- **Acceptance:** from a $120 monthly payment, one action creates an active schedule whose first occurrence is linked to that payment and no new transaction appears.
- **Smallest checks:** C; E(`recurring.spec.ts`).

## P3 · FINX-05: quick-capture paths (voice and notification text)

- **FinX:** `POST /api/ai/parse-speech` turns a dictated phrase into transaction, goal or goal-contribution fields (CHANGELOG v1.3.0; [aiSchemas.js#L60](https://github.com/IT-BAER/finx/blob/9c89557/utils/aiSchemas.js#L60)); `POST /api/ai/parse` extracts a transaction from the text of a bank-app notification, which the Android app captures ([privacy policy#L49-L54](https://github.com/IT-BAER/finx/blob/9c89557/docs/privacy_policy_android.md#L49)); `POST /api/ai/ocr` reads a receipt photo. All three go through OpenRouter with an admin-only default gate, per-user hourly/daily limits, input sanitising and delimiting, a Zod check of the model's reply and a token audit line ([routes/ai.js#L13-L44](https://github.com/IT-BAER/finx/blob/9c89557/routes/ai.js#L13), [aiSanitize.js](https://github.com/IT-BAER/finx/blob/9c89557/utils/aiSanitize.js)). A paid Android option reminds the user to log a purchase after visiting a shop (geofence, privacy policy line 31).
- **FlyBudget today:** receipt photos are read by a local Ollama vision model and can create a transaction ([receiptReader.ts#L1-L5](../../server/src/services/receiptReader.ts#L1), [createTransactionFromReceipt](../../server/src/services/receiptService.ts#L271)), so receipt capture is at parity and stricter on privacy (nothing leaves the owner's network). There is no speech path and no notification-text path: `grep -i "SpeechRecognition|dictat"` and `grep -i "notification text|parseNotification"` find nothing in `client/src` or `server/src`. Up sync covers Up accounts; cash and non-synced accounts need a form.
- **Why it matters:** low for an Up user; real for cash, shared-card and non-Up spending entered at the till.
- **Seam:** a `POST /api/transactions/draft` that sends dictated or pasted text to the same configured Ollama address and model as the receipt reader (reuse `cleanOllamaUrl`, the reply size cap and `READ_TIMEOUT_MS`) and returns fields for the existing add dialog to confirm. The browser's `SpeechRecognition` can fill the text where available. Draft only, never auto-create.
- **Invariants:** off until the receipt reader is on; text never leaves the configured address; model output only fills empty fields and amounts are parsed by `parseCents`, never by the model; a person confirms every draft.
- **Acceptance:** "twelve fifty at the bakery" yields a draft of 1250 minor units with payee suggestion and no saved transaction; malformed model output is rejected.
- **Smallest checks:** S(new test beside `receiptReader.test.ts`); C. Treat as optional: the MCP token route already lets an external assistant propose categories.

## P3 · FINX-06: in-app question-and-answer assistant

- **FinX:** `POST /api/ai/chat` runs a bounded tool-calling loop (`query_transactions`, `get_category_breakdown`, `get_account_balances`, `list_categories`) scoped to the signed-in user plus data shared with them, with a not-advice system prompt, at most 4 tool rounds, 500 output tokens, the last 8 messages only, an optional monthly cost ledger and cap (`ai_chat_usage`, migration 020) ([aiChat.js#L6-L47](https://github.com/IT-BAER/finx/blob/9c89557/services/aiChat.js#L6), [#L57](https://github.com/IT-BAER/finx/blob/9c89557/services/aiChat.js#L57)). Nothing is persisted.
- **FlyBudget today:** read-only and categorise/organise tokens plus an MCP endpoint let an external assistant query the budget ([READ-ONLY-ACCESS.md](../READ-ONLY-ACCESS.md), [mcp.ts](../../server/src/routes/mcp.ts#L20)). There is no chat surface in the app: `grep -i "runChatTurn|ChatPanel|tool_calls"` finds nothing in the client or server (the one `/api/chat` hit is the Ollama call in `receiptReader.ts`).
- **Why it matters:** only convenience; the owner already reaches the budget from an assistant through MCP, with change sets and undo that FinX's chat lacks (its chat is read-only by design).
- **Seam if ever wanted:** a panel that calls the existing MCP tool functions in-process with a read token's scope, against the local Ollama model, with FinX's guard rails copied as requirements (bounded rounds, sanitised input, no writes).
- **Decision:** not recommended while MCP is the supported route. Recorded so the choice is explicit.

## P3 · FINX-07: device lock for the phone web app

- **FinX:** the Android app offers biometric quick access (README line 355; "Biometric authentication data... is processed locally by your device OS", privacy policy). The native implementation is not in the clone.
- **FlyBudget today:** a sign-in lasts 30 days ([`SESSION_TTL_MS`](../../server/src/auth/sessions.ts#L13)); the phone shows balances to anyone who opens the unlocked device's browser. There is a signed-in devices list and remote sign-out ([ServerSettings.tsx#L310](../../client/src/components/settings/ServerSettings.tsx#L310)), but no idle lock, PIN, WebAuthn or hide-amounts mode: `grep -i "inactiv|auto-lock|privacy screen|hide balances"` finds only unrelated "inactive category" text.
- **Seam:** a per-device preference (`preferencesStore`) that blurs the app after N minutes hidden and requires a WebAuthn user-verification prompt (platform authenticator) or the server password to continue. Client-only; no server credential store, so nothing new to leak. A hide-amounts toggle is the smaller first step.
- **Invariants:** convenience lock only, not a replacement for the 30-day session or sign-out; never stores the password; falls back to the password where WebAuthn is missing.

## P3 · FINX-08: live updates across devices

- **FinX:** an in-process SSE broadcaster at `/api/events` (max 5 connections per user, 25 s keep-alive, [utils/sse.js](https://github.com/IT-BAER/finx/blob/9c89557/utils/sse.js)) pushes `transaction:*` and recurring changes to the owner and anyone the data is shared with, and the client invalidates caches ([realtime.js#L67-L73](https://github.com/IT-BAER/finx/blob/9c89557/frontend/src/services/realtime.js#L67)). Its auth is weak (see below).
- **FlyBudget today:** no push channel: `grep -i "EventSource|text/event-stream|WebSocket"` finds nothing in `server/src`, `client/src` or `electron`. Query data is `staleTime: 30_000` ([main.tsx#L31](../../client/src/main.tsx#L31)) and Up sync results appear on the next refetch or focus. Stale-write protection is a separate concern (see [BUD-01](ynab-flybudget-budget-gaps.md)).
- **Why it matters:** small for one owner. Mildly useful when a phone and the desktop app are both open, or after a background Up sync.
- **Seam:** if built, an authenticated `GET /api/events` that sends only "something changed" (entity name), authenticated by the session cookie, never a token in the query string, with the client calling `queryClient.invalidateQueries`. Reverse proxies and the multi-user gateway must pass it unbuffered.

## P3 · FINX-09: showing one account to another person (decision, not defect)

- **FinX:** an owner shares with another user by short share code at `read` or `read_write` level, optionally limited to chosen sources ([sharingController.js#L68](https://github.com/IT-BAER/finx/blob/9c89557/controllers/sharingController.js#L68), [utils/access.js](https://github.com/IT-BAER/finx/blob/9c89557/utils/access.js)). A write to a shared source creates a mirrored opposite transaction in the owner's ledger, linked by `mirrored_from_transaction_id` and kept in step on edit and delete ([utils/transactionMirror.js](https://github.com/IT-BAER/finx/blob/9c89557/utils/transactionMirror.js), migration 016).
- **FlyBudget today:** by design the opposite. Multi-user mode gives each person a separate budget process and database, and "no page, API, export, MCP endpoint, access token or backup of one budget can reach the other's" ([MULTI-USER-PLAN.md#L32](../MULTI-USER-PLAN.md#L32)). Households record shared expenses, splits and settlements without giving the other person access ([HOUSEHOLDS.md#L4](../HOUSEHOLDS.md#L4)). There is no account share or counter-entry between budgets.
- **Why it matters:** only if a partner wants to see one joint account in their own budget. For Up 2Up accounts both people can sync the account from the bank side, which avoids the problem.
- **Decision:** leave as is. If it is ever needed, the safe shape is a one-way read-only feed of a single account's transactions from one budget into another as imported rows with stable ids (so nothing in the owner's budget becomes reachable), not FinX-style write access. FinX's own model has a visible cost: categories are shared globally by name across users ([models/Category.js#L47](https://github.com/IT-BAER/finx/blob/9c89557/models/Category.js#L47)).

## Where FlyBudget leads

All of these are source-evidenced from the files named.

- **Money representation.** FlyBudget stores integer minor units everywhere ([schema.ts#L90](../../server/src/db/schema.ts#L90)) and has BigInt rate conversion, largest-remainder allocation and property tests. FinX stores `NUMERIC(10,2)` (exact in the database, capped at 99,999,999.99) but reads every value back with `parseFloat` and computes in JavaScript floats (`transactionController.js#L525-L526`, `#L1355-L1356`; every model constructor, e.g. [Goal.js#L9-L10](https://github.com/IT-BAER/finx/blob/9c89557/models/Goal.js#L9)), rounding with `Math.round(x*100)/100`.
- **Currency.** FinX has no currency column. The displayed currency follows the interface language: USD for English, EUR for every other language ([useTranslation.js#L89-L90](https://github.com/IT-BAER/finx/blob/9c89557/frontend/src/hooks/useTranslation.js#L89)), and the AI chat is told never to convert. An AUD owner would see dollars labelled USD. FlyBudget has per-account currencies, rate books and main-amount values.
- **Budgeting.** FinX has a single `budget_limit` per category and a "Safe to spend" figure computed as this month's income minus expenses minus remaining recurring expenses ([transactionController.js#L1337-L1380](https://github.com/IT-BAER/finx/blob/9c89557/controllers/transactionController.js#L1337)), which ignores account balances and prior months and which FinX removed from its own dashboard in v1.0.0 (the endpoint and card components remain). FlyBudget has envelope accounting, Ready to Assign, targets, card funding and payday plans.
- **Goals.** FinX goals are free-standing counters fed by manually entered contributions and database triggers ([migration 009](https://github.com/IT-BAER/finx/blob/9c89557/database/migrations/009-add-goals.sql)); they do not move or reserve money. FlyBudget goals are tied to category funding ([CATEGORY-GOALS.md](../CATEGORY-GOALS.md)).
- **Offline data safety.** FinX's queue gives up on an item after five failed attempts and silently deletes it ([offlineStorage.js#L402-L407](https://github.com/IT-BAER/finx/blob/9c89557/frontend/src/utils/offlineStorage.js#L402)); an offline edit to a transaction that was deleted on the server is turned into a new transaction (`#L464-L520`), so a deletion can be undone by a stale device; queued creates carry no idempotency id, so a lost response can duplicate, and the code instead removes local "duplicates" by matching description, amount, type and date ([offlineAPI.js#L1031-L1062](https://github.com/IT-BAER/finx/blob/9c89557/frontend/src/services/offlineAPI.js#L1031)), which can also hide two genuine identical purchases. FlyBudget gives every queued item its server id so sending twice is harmless ([outbox.ts#L8-L12](../../client/src/offline/outbox.ts#L8), [transactions.ts#L128](../../server/src/routes/transactions.ts#L128)), keeps refused items visible with Try again and Discard, and makes edits and budget changes wait ([offline.mdx](../../website/docs/offline.mdx)).
- **Recurring correctness.** FinX's processor skips an occurrence if _any_ transaction of the same user has the same amount on that date ([recurringProcessor.js#L106-L110](https://github.com/IT-BAER/finx/blob/9c89557/services/recurringProcessor.js#L106)), which wrongly suppresses a bill when an unrelated purchase matches. FlyBudget links by schedule/occurrence id, weekend rules, flexibility windows, precision types and discovery.
- **Auth and session handling.** FinX keeps its JWT in `localStorage` ([auth.jsx#L47](https://github.com/IT-BAER/finx/blob/9c89557/frontend/src/utils/auth.jsx#L47)) and puts it in the SSE URL query string ([realtime.js#L73](https://github.com/IT-BAER/finx/blob/9c89557/frontend/src/services/realtime.js#L73), [authSSE.js#L8-L18](https://github.com/IT-BAER/finx/blob/9c89557/middleware/authSSE.js#L8)), where proxies and access logs record it. FlyBudget uses hashed server-side sessions in cookies, a trusted-device lockout defence, scoped hashed access tokens and a signed-in devices list.
- **AI privacy.** FinX sends receipt photos and notification text to OpenRouter (its default model `deepseek/deepseek-chat`, [aiChat.js#L21](https://github.com/IT-BAER/finx/blob/9c89557/services/aiChat.js#L21)), and a consent dialog and no-training flag stand in for control. FlyBudget's reader talks only to an Ollama address the owner names.
- **Breadth.** Reconciliation, splits, transfers with reviewed suggestions, payees and rules, bank sync (Up, Enable Banking, Plaid, SimpleFIN), households, tax claims, investments, forecasts, custom reports, change sets with undo, backups with restore, CAMT import with duplicate memory, HA packaging, and a desktop app. FinX has no equivalent of most of these: it has CSV/JSON import with duplicate detection and an export, and its bank sync is a managed-hosting feature that is not in the repo (migration 019 comment).
- **Tests.** FinX has 22 small Node test files, one of which asserts `1 + 1 === 2` (`tests/smoke.test.js`), and only three use an HTTP request helper. FlyBudget has 104 unit and component test files and 40 Playwright specs.

Takeaways: FinX's phone navigation (always-reachable add, swipe between top pages, haptics) is more thumb-first than FlyBudget's drawer, which is the substance of FINX-03. Nothing in FinX's desktop UI is ahead of FlyBudget's. Localisation is a difference rather than a gap for an Australian owner; adding an i18n layer would touch every string and is not recommended.

## Not gaps (checked)

- Receipt to transaction, merchant-to-category memory (FlyBudget has rules, payee default categories and the [category follow-up toast](../../client/src/components/transactions/CategoryFollowupToast.tsx)), CSV/JSON import and export, account opening balances (FlyBudget has reconciliation and adjustments), net worth, upcoming bills, spending-versus-last-month, per-source reports, goals with deadlines, admin user management (single owner), audit log (FlyBudget lists signed-in devices and attributes token changes to the token in change sets, [changeSets.ts](../../server/src/services/changeSets.ts#L19)), and server-side sort/filter with totals.
- The Android app's local-only mode is what the desktop app already gives on a computer; the phone has no equivalent and none is proposed.

## Suggested order

1. **FINX-01** first. It is a small, testable change next to existing code, it removes a hidden "restart to apply" behaviour, and FINX-02 depends on it.
2. **FINX-03** (manifest, icons, safe-area, phone add button). Mostly static files and one component, and it directly improves the phone story the brief names as the main shortfall. Verify installs on a real Android phone and iPhone.
3. **FINX-02** on the FINX-01 timer, Home Assistant only, off by default.
4. **FINX-04** as a small follow-up using the schedule dialog and discovery code.
5. Record decisions on **FINX-06** (no), **FINX-09** (no) and **FINX-08** (only if two-device use becomes common). Do **FINX-07** as a hide-amounts toggle if wanted. Do **FINX-05** only after the receipt reader is in regular use.

No application release, version bump or live-budget change follows from this documentation-only investigation.
