# FlyBudget adaptation map for the Monarch investigation

Inspected 22 October 2026. This is a selective source review of the current working tree. It is not a statement that Monarch implements any particular mechanism. Monarch observations and recommendations must remain separate. No app changes, live data, migrations, tests, releases or deployments were performed for this map.

## Forecast architecture already present

[forecastService.ts](../../server/src/services/forecastService.ts) explicitly reads the same budget/payday definitions used elsewhere: personal on-budget liquid accounts, future register entries, pending schedule occurrences, active payday plans and household shares. The service is read-only. Currency conversion, closed-account exclusion and missing-rate warnings are visible in its cash-position calculation. The API comments state that scenario assumptions are not saved.

That makes persistent named scenarios a plausible **recommendation**, not an existing feature established here: add an additive scenario-definition model with versioned assumptions, then call the current read-only calculation service. Saving a scenario must never create transactions, alter category allocations or edit goals. Keep estimate labels, source freshness, assumptions and shortfall explanations next to the chart.

## Recommended implementation order

1. **P0 — complete the evidence register.** For each observed Monarch action record entry point, prerequisites, trigger, overlay/navigation result, fields/defaults, validation, save/cancel behavior, persistence scope and evidence ID. Mark blocked/account-dependent paths. Do not turn an unexplored action into a claimed specification.
2. **P1 — shared navigation and interaction consistency.** Build on URL transaction filters, existing panels, shared modal primitives and chart drill-through. Use one vocabulary for dates, amounts, filters, save scope, pending states and empty states. Preserve keyboard focus and explicit confirmation for destructive actions.
3. **P1 — forecast usability.** Compare existing FlyBudget controls against verified forecast evidence; add only missing explanations or interactions first. Test calculations with disposable mock budgets, especially overlap between scheduled income, future register entries and household obligations.
4. **P2 — planning persistence.** If trial evidence demonstrates useful saved plans, persist assumptions separately from ledger facts. Show the chosen baseline and provide reset/duplicate/compare actions with clear scope. Keep annual budget plans separate from available cash.
5. **P2 — recurring and goal feedback.** Explain why an item was suggested or matched, how progress is funded, and what lifecycle actions change. Reuse current discovery, matching and lifecycle services.
6. **P3 — investments.** Scope positions, valuation dates, quotes, currencies, transfers, deposits/withdrawals and performance methodology before building a dedicated tab. Treat this as a separate feature rather than deriving performance from net-worth charts. **Status:** scoped and shipped as manual holdings, prices and tax lots with unrealized gain only; see [INVESTMENTS.md](../INVESTMENTS.md) for the decisions and what remains deferred.

No new dependency or architecture rewrite is justified by this selective mapping alone. Future implementation should follow feature branches, focused verification and the repository's release process; this research document itself needs no app release.
