### F-01 · P1 · UX / finance presentation: the dashboard "left to spend this month" includes savings-goal envelopes

- **Location:** `client/src/utils/leftToSpend.ts:9-16`, `client/src/components/dashboard/DashboardStatus.tsx:42`, `SummaryStats.tsx:45-64`
- **Evidence:** On the demo budget the headline reads "You have **$60,967.34** left to spend this month"
  . By independent per-group sums,
  **$52,977.79** of that is the "Savings Goals" group (emergency fund, holiday). Everyday envelopes hold
  $7,989.55. Ready to Assign is $1,426.51. The same number appears twice on phones: headline and stat card.
- **Root cause:** `leftToSpend` sums every non-income envelope's Available, with no notion of an envelope's purpose.
- **User impact:** The most prominent number in the app overstates spendable money about 7.6×. That
  undermines the core promise for exactly the people least familiar with envelopes.
- **Reproduction:** `DB_PATH=demo.db npm run db:seed-demo`, open `/dashboard`.
- **Recommended correction:** Define the figure explicitly. Recommended: exclude groups or categories that
  are goals or savings, or that have long-horizon targets, and label it "Left for this month's spending".
  Option: show both "for spending" and "set aside". This is an owner decision (I-1).
- **Regression protection:** A unit test on `leftToSpend` with a goal-backed category, plus an e2e
  assertion on the headline for the demo budget.
- **PR history:** Headline added in #119 (UX review); `leftToSpend` predates it.
- **Confidence:** Confirmed.

### F-02 · P1 · State management: the Budget page shows stale envelope figures after a transaction edit

- **Location:** `client/src/hooks/useTransactions.ts:94-97` (update), `:127-136` (delete). Neither invalidates `['budget']` or `['budget-summary']`. `client/src/main.tsx:31` sets `staleTime: 30_000`.
- **Evidence:** In the browser, I recategorised a $9.49 "Coffee" purchase to Groceries in the register,
  then navigated client-side to Budget. Coffee still showed Activity −$17.13 / Available **$88.40** while
  the server returned **$97.89**. It corrected only after 30 s (observed in the browser).
- **Root cause:** Invalidation is hand-maintained per mutation: 338 calls across 64 files, with no rule
  that "anything touching the ledger refreshes the ledger views". The server already exposes a
  `fundingRevision`, but the client doesn't use it to invalidate.
- **User impact:** After categorising, the most common action, users see wrong Available amounts and may
  assign based on them. The server guard prevents overspending Ready to Assign, so this is display
  only, but in the core workflow.
- **Reproduction:** As above, within 30 s.
- **Recommended correction:** One `invalidateLedgerViews(qc)` helper (budget, budget-summary, review,
  accounts, reports, goals, dashboard) used by every transaction, assignment, transfer, household and
  import mutation. Better still, put it in the global `MutationCache.onSuccess`, which today only
  invalidates `goals`, or invalidate when the `revision` in a mutation response changes.
- **Regression protection:** An e2e test: load Budget, recategorise in the register, return, assert the
  figures equal the API's. A unit test that every mutation hook in `hooks/` routes through the helper.
- **PR history:** The pattern is inherited. The ledger revision was introduced in #65.
- **Confidence:** Confirmed.

### F-03 · P1 · UX / finance: a first Up import makes day one start with "Cover overspent envelopes" and a Ready to Assign above cash

- **Location:** `services/budgetService.ts:122-194` (cash overspending is not deducted in its own month, by design); `utils/reviewNext.ts`; Welcome/Up flow.
- **Evidence:** On a fresh budget on 3 Nov, importing the mock Up history produced:
  - Review → "Do this next": **1. Cover overspent envelopes $943.37**, **2. Assign $13,842.51**, **3. Reconcile 2 accounts**.
  - Budget shows Rent −$900 available and Ready to Assign **$13,842.51**, while the accounts hold
    **$12,899.14**.
  - If the user assigns everything shown, December starts at −$943.37.
- **Root cause:** The YNAB overspending rule (#57/#61) applied to history that predates the user's first
  budgeting act. The budget start defaults to all history.
- **User impact:** Persona A's first experience is a red task list and a number they can't actually use.
  This is HANDOVER open item 6. **Still reproducible.**
- **Recommended correction:** On a first bank connection, offer "Start budgeting from today". Set
  `budget_start_month` to the current month and treat this month's pre-connection spending as history:
  the existing `sinceBudgetStart` already supports this. Alternatively, hide "Cover overspent" until
  the first assignment. Owner decision I-2.
- **Regression protection:** An e2e on `first-import.spec.ts`: after connecting Up mid-month, Ready to
  Assign ≤ cash and no "Cover overspent" task.
- **PR history:** #57, #61, #79, #82; noted in HANDOVER item 6 after the 31 Oct review.
- **Confidence:** Confirmed.

### F-04 · P1 · Cross-feature: deleting one Up transaction blocks every assignment in the budget

- **Location:** `services/transactionHelpers.ts:102-120` (deletion remembered, #97); `services/accountIntegrity.ts` and `budgetMoves.ts:219` (guard, #69); `TransactionDetailPanel.tsx:550` (confirm copy).
- **Evidence:** Deleting a single $5.50 Up row (allowed, and remembered so it isn't re-imported) made the
  register differ from Up's balance. The next assignment returned **409** "Reconcile account balance
  discrepancies before assigning more money…", as did moves, payday and card funding.
  Restoring via `POST /up/review/restore` unblocked it (scripted against a disposable server).
- **Root cause:** Two individually correct features. "Delete stays deleted" and "never fund from an
  unverified balance" combine, and nothing tells the user at delete time that funding will stop.
- **User impact:** A routine clean-up of an apparent duplicate silently freezes budgeting. The recovery
  path (Settings → Connected Banks → Up review → Restore, or reconcile with an adjustment) is obscure.
- **Recommended correction:**
  1. Confirm copy for bank rows: "Up still has this. Your balance won't match Up until you restore it,
     and assigning money will pause."
  2. Make the Budget block banner link straight to Up review's deleted list.
  3. Owner decision I-3: offer "Hide from budget" (excluded from categories, still counted in the
     balance) as the default instead of delete.
- **Regression protection:** An e2e: delete an Up row → the Budget banner names the row and offers
  Restore → Restore → assignment works.
- **PR history:** #69, #97.
- **Confidence:** Confirmed.

### F-05 · P1 · Data preservation: "Full Backup" calls itself complete but excludes every Files byte

- **Location:** `client/src/components/settings/DataExport.tsx:140-147`; `docs/FILES.md` §2; `services/backupService.ts` (format 23).
- **Evidence:** The copy says "Download a **complete** JSON backup of all your data… neither are receipt
  photos". Since Files (#112) the backup also omits PDFs, documents, spreadsheets and videos: metadata
  only, `hasFile: false` elsewhere. Only HA backups, a cold copy of the data folder, or Files →
  **Download all** keep them.
- **User impact:** A user restoring from the in-app backup after losing the machine loses all
  documents, including tax evidence the app encourages them to keep there.
- **Recommended correction:**
  1. Fix the copy now: drop "complete", name what's excluded, and link to Files → Download all.
  2. Owner decision I-6: offer a "Backup with files" ZIP (JSON plus content-addressed files) using the
     existing `ZipWriter`.
- **Regression protection:** A test that the backup panel text mentions Files when any document exists.
  A restore test that a ZIP backup round-trips bytes.
- **PR history:** #54, #112.
- **Confidence:** Confirmed (copy and docs).

### F-06 · P2 · Security hardening: outside server mode, a non-loopback bind exposes the API to Host-header spoofing

- **Location:** `server/src/config.ts:24`, `middleware/security.ts:39-62`, `index.ts:154-163`.
- **Evidence:** I started a disposable instance with `FLYBUDGET_HOST=0.0.0.0` and server mode off. From
  the container's network address:
  - a plain request got "Forbidden host";
  - with `Host: localhost:3903`, `GET /api/accounts` returned **200**;
  - with the same header, `POST /api/accounts` **created an account**.

  Startup printed no warning.

- **Root cause:** In non-server mode the only network control is a Host check. Startup refuses
  gateway-without-loopback, but not non-server-mode-without-loopback.
- **User impact:** Needs a misconfiguration (Docker and HA set server mode), but the result is full
  unauthenticated read/write on the LAN.
- **Recommended correction:** At startup, throw unless `serverMode || isLoopback(listenHost) || FLYBUDGET_API_TOKEN`.
- **Regression protection:** A `security.serverMode.test.ts` case asserting startup refuses the combination.
- **Confidence:** Confirmed.

### F-07 · P2 · Design system: `Input`/`Select` drop their styling when given `className` (still on main), and the primitives can't merge classes

- **Location:** `client/src/components/ui/Input.tsx:6-12`; consumers: `pages/Files.tsx:285,299,313,320`, `components/tax/TaxClaimSection.tsx:85`.
- **Evidence:** `className={inputClass} {...props}` lets a caller's `className` replace the base classes.
  PR #120 (open) fixes it by concatenating, with `w-full` as the default **only when no className is
  passed**. Every caller passing any class, for example `mt-2`, silently loses full width. #120's
  `Files.tsx` adds `w-full` by hand to compensate. `Button` also concatenates without merging, so
  `className="h-12"` against the new `h-10` resolves by CSS emission order, not intent.
- **Root cause:** There is no class-merging convention (no `cn`/`tailwind-merge`) and no width or size
  props.
- **Recommended correction:** Adopt one `cn()` (tailwind-merge) in all primitives, or give primitives an
  explicit `width` prop. Keep base classes first and caller classes last. Add a lint rule that forbids
  `{...props}` after `className`.
- **Regression protection:** Component tests: `<Input className="mt-2">` keeps border, height and
  `w-full`; `<Button className="h-12">` is 48 px.
- **PR history:** The bug predates the fork (`52cc4b6` "extract shared Input/Select"). #120 is the partial fix.
- **Confidence:** Confirmed.

### F-08 · P2 · Tests / maintainability: no linter runs

- **Location:** No ESLint config or `lint` script in any package. CI runs `tsc`, tests and Prettier only.
  There are 12 `eslint-disable-next-line react-hooks/exhaustive-deps` comments (e.g. `ContextMenu.tsx:115`,

### F-10 · P2 · Performance and reliability: Up sync re-downloads the full history every run

- **Location:** `services/upService.ts:9-10,77-80`; `upSyncService.ts:144`; polling `UP_POLL_INTERVALS` (15–240 min).
- **Evidence:** `getUpTransactions` pages through all history (100 per page, up to 1,000 pages or
  100,000 rows) for every mapped account, on every sync. Beyond 100k rows a sync fails outright.
- **Impact:** For a multi-year Up user this means hundreds of sequential requests per sync, more exposure
  to Up rate limits (429 → backoff → stale data), and slower HA startup.
- **Recommended correction:** Use `filter[since]` from the latest settled date minus a safety window
  (e.g. 14 days), plus a periodic full sweep (weekly, or on manual "Full resync"). Keep the whole-account
  validation within the fetched window.
- **Regression protection:** Up mock call-count assertions for incremental vs full syncs.
- **PR history:** HANDOVER item 6.
- **Confidence:** Confirmed (code); impact Probable (not load-tested against Up).

## E. User-journey friction report

### Persona A: first-time Australian Up user (driven on a 390 px phone)

**Works well:**

- The server-mode setup screen explains where the setup code is.
- Welcome is now Up-first with a 3-step token explanation. "Read-only: Allotment can't move your money" is reassuring.
- Mapping and import completed in one pass: 175 rows, categorised from Up's own categories, pay detected ("Looks like pay from … every 14 days. One tap puts it in Pay").
- No console errors and no layout overflow.

**Friction:**

- **Day-one red task list** (F-03): "Cover overspent envelopes $943.37" before the user has budgeted anything. _Functional defect in the product model._
- **An unusable Ready to Assign** of $13,842.51 against $12,899.14 cash (F-03). _Functional defect._
- **"Reconcile 2 accounts (161)"** on data the app just verified (F-17). _Design opportunity._
- **"10 possible transfers between your accounts"** needs a manual review (the owner rule forbids silent linking; the register offers a Review link). _Design opportunity:_ one reviewed list at import time (HANDOVER item 6).
- **Budget's first screen on a phone** stacks the template question ("Do you rent or own?"), a "No money assigned" hint and the yellow hero, and only then the envelopes. _Design opportunity._
- **The headline figure later misleads** once goals fill up (F-01).

### Persona B: existing user (demo budget, several months, fortnightly pay, Savers)

**Works well:**

- Budget desktop is dense but clear: the Expected / Activity / Available columns and the "−$2,300 expected" notes for bills are helpful.
- Move money, undo and the revision guard behave correctly.
- The register's inline category editing is fast.
- Safe mode is reliable.

**Friction:**

- **Stale Budget after recategorising** (F-02). _Defect._
- **Delete one bank row and assigning stops** with a message that points to reconciliation (F-04). _Defect in integration._
- **Same number, four names** across Budget and Review (F-09). _Content defect._
- **Seven ways to assign** (inline, Auto-assign, "Put the rest in…", Move money, payday plan, targets, income review). It's unclear which to use when. _Design opportunity_ (F-13).
- **Review vs Budget vs Dashboard "Get started"** each have their own next-action list. _Design opportunity._

### Persona C: advanced household user

Exercised through code, docs and the passing e2e suite; not re-driven by hand.

**Works well:**

- Household entries are attribution only. They never write ledger rows, so a shared expense can't be
  double-counted _in the ledger_.
- Settlements categorised as income are refused (`householdService.ts:271-281`).
- Combined households keep each person editing only their own entries.
- Safe mode and the token scopes are coherent.

**Friction:**

- **Personal reports show the gross expense.** The partner's repayment arrives as an uncategorised
  inflow, which goes to Ready to Assign, unless the user categorises it back to the expense category.
  The "Spending" report overstates personal spending and "Income" includes repayments. Documented as a
  deliberate model ("Do not add this report's shares…") but invisible in the UI. _Design opportunity_ (I-8).
- **Six ways to share** (F-13), and an empty Household page that asks for "People, one per line; put
  yourself first" in a textarea. _Design opportunity._
- **Files are not in the in-app backup** (F-05). _Data-preservation defect in messaging._

## J. Final verdict

1. **Is Allotment architecturally coherent?** Mostly. The financial core is coherent: one cached ledger,
   one funding guard, shared write helpers, documented invariants. Coherence weakens at the edges:
   several services per action family, four sync providers with uneven safeguards, a hand-written
   token policy, and a client whose freshness depends on 338 manual invalidations.

2. **Are financial calculations and data-preservation guarantees well enough tested?** The engine is
   well tested for its documented rules, and every independent check I ran agreed with it. The tests
   are weakest where features meet: transfers, cards, splits and households in randomised ledgers; sync
   idempotency as a property; delete-then-fund; backup with files. Data-preservation code (identifiers,
   migrations, deleted-import memory) is careful. The backup _messaging_ is not (F-05).

3. **Have successive additions introduced unnecessary duplication, fragility or debt?** Yes, moderately.
   The clearest cases are the share and assign paths (F-13), overlapping onboarding systems (F-12), the
   token exception growth (F-18), and the F-04 interaction where two correct features combine into a
   trap. The rate (often several feature PRs a day, merged within minutes) outpaced consolidation.

4. **Does the interface behave consistently across screens and devices?** Responsively, yes: no overflow
   from 320 to 1440 px, coherent dark mode, and keyboard menus. Visually and verbally, not yet: primitive
   bypasses, off-scale type, two date formats, mixed casing, and four names for one number.

5. **Are navigation and onboarding intuitive for someone new to envelopes?** Getting connected is now
   good. Understanding the result is not: the first screen after import shows overspending and a Ready
   to Assign the user doesn't have, and the dashboard's headline later overstates spendable money.

6. **Does it feel like one designed product?** It looks like one: the brand, palette and iconography
   hold. It doesn't yet behave like one. Similar tasks take different shapes on different screens, and
   the same concept is explained in different words.

7. **Five highest-impact improvements:**
   1. Ledger-aware cache invalidation (F-02).
   2. An honest "left to spend" (F-01).
   3. A first-connection budget start (F-03).
   4. A delete/restore flow that can't silently freeze funding (F-04).
   5. One primitive and terminology standard (F-07 + F-09), enforced by lint (F-08).

8. **Must be resolved before calling it release-ready for people other than the owner:**
   - F-01 to F-05.
   - F-06 (startup refusal, small).
   - Merge or replace #120's primitive fix.

   The P2 test additions in F-16 should land before the next change to the ledger model.
