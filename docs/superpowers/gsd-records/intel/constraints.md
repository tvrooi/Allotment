## Assistant endpoints and audit log (policy table)
- source: docs/ASSISTANT-ENDPOINTS.md
- type: api-contract
- content: Access-token writes go only through `/api/assistant/do/<route path>`. `assistantDispatch` (`routes/assistant.ts`) rewrites to `/api/<path>` once and sets `res.locals.viaAssistant` (no header can set it). `requireSession` matches a row of `ASSISTANT_ACTIONS` (`auth/assistantPolicy.ts`): each row has a stable name, narrowest scope, owner-facing summary, `matches` (method, path, body shape; reads nothing) and optional `check` (budget-dependent). No match: 403 logged `refused`. A row with a check re-runs it as the first step inside the write's own DB transaction (`assistantGuard`, since 0.2.0-up.127); a change since step 4 gives 403 "This changed before it could be saved: ..." and nothing is written. A read token's write is refused outright; the owner also gets 403 from the endpoint. `tokenAllows` (`auth/accessTokens.ts`) answers reads only.
- policy rows (scope, allows): `categorise_transaction` (categorise; `PUT /transactions/:id` with only `categoryId`, past transaction); `manage_categories` (categorise; create category/group, edit category fields, rename group); `undo_change_set` (categorise; `POST /change-sets/:id/undo`, token's own only); `rule_dry_run` (organise; `POST /rules/test`, `/rules/preview`); `propose_rule` (organise; `POST /rules` with `enabled:false`); `edit_proposed_rule` (organise; `PUT /rules/:id` on a disabled rule, never enabling/reordering); `apply_rule` (organise; `POST /rules/apply`, one category-only rule, uncategorised past rows); `payee_default_category` (organise; `PUT /payees/:id` only `defaultCategoryId`); `payee_logo` (organise; only a valid `logo`, never removing); `link_transfer` (organise; `POST /transactions/transfers/link` for a server-suggested pair); `suggest_assignments` (organise; `POST /budget-proposals`, owner applies); `claim_tax_deduction` (organise; `PUT /tax/claims/:id` on unclaimed past transaction); `household_contribution` (organise; linked to a past deposit into the household, exact amount); `own_household_contribution` (organise; own unlinked contribution up to what is owed); `propose_change` (organise; `POST /assistant/proposals`).
- Organise tokens read tax paths (`taxReadAllows`, including `GET /tax/home/:fy`). No policy row writes working-from-home hours or lodges a year.
- Rules for the table: every row is an owner-approved exception; never add a writing, settings, backup, auth or bank row; never rename a row (names stored in log); a new row needs an allowed case and nearest refusal in `auth/assistantPolicy.test.ts`, tool tests (`routes/assistantTools.test.ts`, `routes/accessTokens.test.ts`) and its name in the list in `routes/assistant.test.ts`; a row that reads the budget has a `check` and the writing service calls `assistantGuard(res.locals)` first inside its transaction.
- Audit log: table `assistant_actions` (migration 0069, columns from 0071), written by `services/assistantLog.ts`: time, token id/name, scope, row name, MCP tool, method, path, outcome (`refused|applied|failed`), status, reason. No request bodies kept; newest 5,000 rows kept; never in backups; no token can read it. Owner reads `GET /api/assistant/activity` (`limit`, `offset`) and Settings > Server > Access tokens > Assistant activity.
- Proposals (`assistant_proposals`, `services/assistantActions.ts`; at most 50 waiting) listed under "Waiting for you"; owner applies/declines via `POST /api/assistant/proposals/:id/apply|decline`. Types: depreciating asset proposal (MCP `propose_tax_asset`), `household.remove_entries`, `household.share_bills`, `household.unlink_transfers`, `household.reconcile` (MCP `propose_household_reconciliation`; refused at apply if any balance changed since proposed). Each holds up to 50 items, is checked when proposed, lists every item, applied whole in one DB transaction or not at all.
- Phases: 1 done (0.2.0-up.99; policy table/log from #140 in up.101); 2 done (proposals; household corrections up.114); 3 done (0.2.0-up.127, checks inside the write).

## Assistant endpoints phase 3: checks inside the write
- source: docs/ASSISTANT-PHASE-3.md
- type: protocol
- content: Status built in 0.2.0-up.127 (designed 6 Nov 2026; owner took every recommendation). Option A chosen: each budget-reading row keeps one predicate split into `matches(method,path,body)` and `check(request)`; `requireSession` runs it early (logged refusal) and the writing service re-runs it as first statement in its `db.transaction` through `assistantGuard(res)` (returns nothing for owner; for tokens a function that throws `AssistantRefusal` 403). - Tests: new `auth/assistantPolicy.test.ts` (allowed case + nearest refusal per row; interleaving case per budget-reading row via middleware that changes budget after the early check; each must 403, change nothing, log `refused`); owner writes unchanged. One server-only PR, no migration, no backup change, no UI.
- Open follow-up (decision 5, not built at time of writing): MCP change-set race (transactions PUT returns the replaced category read inside its transaction; MCP records that).

## Budget review, buffer and guided setup (phases 6F-6G)
- source: docs/BUDGET-REVIEW.md
- type: api-contract
- content: Review page is read-only; every figure comes from `fundingState` (`server/src/services/reviewService.ts`). Routes `GET /api/review`, `GET /api/review/buffer`, `GET /api/review/guide`, read-only, behind the budget guards; demo serves the same routes. Needs-attention items: uncategorised (`uncategorized`), overspent (`overspent`), targets underfunded, card debt without reserve (`paymentShortfall` + uncovered), assigned to later months (`futureAssigned`), unassigned/over-assigned (`toBeBudgeted`). `kept` (Keep overspending) categories stay listed until covered. Missing exchange rates mark review incomplete. Undo/Redo change only category. Sort-repeated-payees excludes household and off-budget accounts, transfers, split parents, household-linked entries; "Also apply to future transactions" off by default. Category-group filter only affects overspent, target shortfalls, later-month details; no authorship is recorded (shared password session).
- Guided setup: six steps derived live (nothing stored): confirm balances, cover what is due before next income (window up to but not including next income date: next payday of any active plan or next pending scheduled income, else 14 days; outcomes "No tracked bills due before {date}", "All tracked bills before {date} are funded", "Can't confirm coverage: N bills need categories"; `guideState` returns `coverage` and `excludedBills` from `billCoverageDetail`; household pool bills listed as information, never block), assign money you have, prepare for irregular expenses, check categories, move money.
- Buffer/runway ("cash coverage with no income"): cash in budget accounts = personal on-budget checking, savings, cash, card accounts; debt on a card enrolled in card payments does not net (only positive balance counts); restricted money (balance-by-date or recurring-bill target categories, card payment reserves, reviewed card debt without reserve) excluded; `unrestricted` = cash - restricted - card debt without reserve; spending rate = net spending over last three complete calendar months excluding restricted, uncategorised debits included; runway days = unrestricted / daily rate; incomplete (no number) when rates missing, history starts after window, a window transaction lacks a rate, or no spending. Retirement/investment/property/off-budget contribute nothing. Money age explicitly not implemented.
- Phase 7 additions: Resume budgeting, Flexibility and resilience card, Extra income (see RESILIENCE.md). Works at 390 px; browser suite checks both.

## Card payment funding (phase 6B)
- source: docs/CARD-PAYMENTS.md
- type: nfr
- content: Payment funding is an explicit, reviewed change per personal on-budget credit card or line of credit (Budget > Card payments > Review setup). Preview shows existing debt, cash to reserve, remaining payment shortfall, unassigned before/after; nothing changes until "Enable payment funding" is applied; preview expires on relevant financial edits and calendar-day changes. Setup adds a payment category, a dated review record and only the initial payment assignment the user approved; existing transactions/opening balances/bank IDs/reconciliation/assignments untouched. Cards without reviewed setup keep 6A conservative net-debt treatment.
- Invariant: `resources = unassigned + expense envelopes (signed, less credit overspending) + positive payment reserves + later assignments`. Credit overspending is card debt, never deducted from Ready to Assign. A funded purchase consumes its expense envelope and moves backing cash into the card's payment envelope; linked repayment is an internal transfer consuming payment funding and cash. Unfunded purchases create a payment shortfall (needs Fund debt or Move money). Payments beyond reserve show "Payments without funding".
- Calculation order: as-of date; category assignments through that month and cash activity take priority; remaining category resources fund reviewed-card purchases in date, record-creation-time, ID order; later assignment in same month can fund earlier purchases; future assignments and expected income cannot; month-by-month envelope reset applies. Missing rates make funding incomplete and block assignments and setup. Setup retains identities of existing dated parent transactions; automatic funding only for new identities dated on/after setup date; historical views before setup keep previous net-debt model.
- Refunds/transfers: refund reverses unfunded debt first, then releases reserves, surplus becomes prepaid balance; overpayment retained as positive card balance; extra assigned payment cash stays reserved as "Extra reserve"; linked balance transfer between two reviewed cards moves payment funding; cash advances are transfers, not income. Payment categories excluded from ordinary pickers, protected from direct ledger use, deletion, reclassification as income, and movement outside personal credit-account scope. Record repayments as linked transfers.
- UI: reviewed card's payment envelope is a row in the budget table's "Card payments" section and a phone card (BUD-09, `Budget.tsx`, `PhoneBudget.tsx`); notes from one function `cardNotes` in `utils/cardRows.ts`, rendered by `CardRowNotes.tsx`; nothing recomputed on client; section outside expense totals.
- Compatibility: additive migration creates no setup/assignments/transactions; portable backup version 8 includes setup records and baseline identities; older backups restore without reviewed setups; restore invalidates stale undo and setup previews.

## Category-funded goals (phase 6C)
- source: docs/CATEGORY-GOALS.md
- type: schema
- content: Existing goals remain manual tracking goals (saved amount, optional account reference preserved; account link reserves nothing). A goal can link one expense category; each category funds at most one goal; income and card-payment-reserve categories cannot (API, unique DB index and additive migration constraints enforce). Unlink/delete category restores manual value without rewriting transactions/assignments. Linked goal uses today's availability from shared envelope/card service in minor units; funded progress is the positive portion of availability; negative stays a deficit; future-month assignments do not fund today's goal; no independently editable funded amount. Missing exchange rate gives unknown funded progress with incomplete warning. Backup format 9 stores category linkage and untouched manual value, not derived progress; older backups restore as manual goals; restore rejects missing, income, payment-reserve and duplicate category claims before changing the budget. Goals can be paused/completed/retired/replaced (phase 7D, RESILIENCE.md); non-active goal keeps funding and link but gets no target, payday or forecast suggestions. Implementation `0.2.0-up.12`.

## Category targets (phase 6D)
- source: docs/CATEGORY-TARGETS.md
- type: schema
- content: One target per expense category; income categories and card-payment reserves cannot. A target only suggests funding. Types: Monthly amount (same every month); Balance by date (what is missing divided over months left through due month inclusive, rounded up); Recurring bill (like balance by date toward next due date; repeats every N months); Refill to balance. Uses balance carried into the viewed month from the shared envelope service. Example: $1,200 due in six remaining months with $300 reserved needs $150/month; $180 over five months. Recurring due dates advance by whole cycles; day missing in a month falls back to month's last day; passed balance-by-date shows "Target date passed". Deadline arithmetic shared with payday plans' "Target by date" and forecast goal contributions in `server/src/services/fundingMath.ts`. Fund targets previews assignment per underfunded target in budget order capped at money unassigned today (expected income never counted); Apply adds exactly previewed amounts in one transaction through the same guard; stale or repeated preview assigns nothing. Monthly average divides by every month in window including zero-spend months. "Use for the next 12 months" lists every month it would overwrite and applies only if those months still hold reviewed amounts. Targets are in backup format 10; restore rejects targets on missing, income or card-reserve categories and malformed definitions. Implementation `0.2.0-up.15`.

## Pay later payment plans (up.67)
- source: docs/PAYMENT-PLANS.md
- type: schema
- content: A provider (Afterpay, Zip Plus, Klarna, PayPal Pay in 4, Humm) is a small credit account (`type='credit'`, on budget); purchase recorded once in its real category on the provider account; instalments are transfers Up <-> provider with no category; reports count purchase in month of purchase; no BNPL spending. Envelopes: "A plan account gets payment funding when it is created (an empty account needs no review)" — funded purchase moves category money into "<Provider> payment"; Ready to Assign unchanged; unfunded purchase is credit overspending/payment shortfall. Forecast unchanged. Budget page shows unpaid instalments due this month in orange (`expectedInstalments` in `expectedDebits.ts`).
- Data (migration 0057, backup version 21): `payment_plans` (plan account, payment account, purchase row, provider, merchant, total, instalment count, frequency weekly|fortnightly|monthly, first due date, `extra_transaction_ids` JSON); `payment_plan_instalments` (number, due date, amount, `transaction_id`, `previous_json`, `paid_at`; refund-zeroed instalment is settled); `payment_plan_dismissals`. Amounts split equally, odd cents on first instalment; unpaid instalment date/amount editable.
- Linking never guessed: `GET /api/payment-plans/matches` suggests bank rows in the plan's payment account, money out, not transfer/split/adjustment/household/reconciled, naming the provider (`/after\s*pay/i` for Afterpay; "Payment plan" has no pattern), equal to one unpaid instalment within 3 days before to 10 days after due, or several together. Link needs owner confirmation (`POST /:id/link`); makes the bank row a transfer into the plan account (always a new other side), clears category; unlink `POST /:id/instalments/:iid/unlink` restores payee/category exactly and deletes created side; reconciled rows refused.
- Earlier purchases: `GET /api/payment-plans/history?months=12` groups past unlinked provider payments (same account, 12-16 days apart, same amount (first up to 3 cents more), at most four; last payment within 16 days = still being paid); `POST /payment-plans` with `linkTransactionIds` records and links in one DB transaction; reconciled payments locked.
- Refund `POST /:id/refund` (credit on plan account in purchase category; unpaid instalments shrink from last); late fee `POST /:id/fee` (expense on plan account, Bank Fees default; added to next unpaid instalment or new instalment); remove `DELETE /:id` (unlinks payments, deletes created rows; refused while any is reconciled; bank rows never deleted; client undo for "Add a purchase" is this removal).
- Not built: opening debt for plans already underway; Afterpay Pay Monthly (interest-bearing); Zip Pay revolving minimum; read-only tokens see no plan routes; Australian template no longer creates "Afterpay / Zip" for new budgets.

## Desktop updates
- source: docs/DESKTOP-UPDATES.md
- type: protocol
- content: In-app install enabled only for packaged Mac apps whose Developer ID signature verifies; unsigned/ad-hoc and other platforms offer "Download installer" from this fork's public GitHub Releases (`up` preview channel, no GitHub token). Verified signed Mac builds offer "Download update" then "Restart and install"; Later never restarts; quitting does not silently install; updates never touch server DB or key. ## Envelope funding (phase 6A)
- source: docs/ENVELOPE-FUNDING.md
- type: nfr
- content: One calculation service (`fundingState` in `budgetService.ts`, ledger in `budgetLedger.ts`) supplies monthly summary and payday planner. Expense Available = previous Available + Assigned + signed Activity. `ready to assign = resources - sum envelope Available (signed) - later positive assignments`; nothing stored; `readyToAssign.test.ts` checks against independent ledger recompute and that no money figure is fractional. Identity with hold: `toBeBudgeted + envelopes + laterDeduction + held = resources`. `breakdown`: `cash`, `otherDebt`, `cardDebt` (`total`,`reserved`,`unreserved`), `linked`, `everydayEnvelopes`, `setAside`.
- Overspending rule: an envelope ending a month below zero starts the next at zero (`rollOver`). Cash overspending is red in its month, does not lower that month's Ready to Assign, and comes out of next month's once (example: $1,000 received, $700 Food, $300 Rent, $800 spent on Food: Oct RTA $0, Food -$100; Nov RTA -$100, Food $0). Credit overspending is card debt never deducted from RTA. Card payment envelopes count only a positive reserve. Keep overspending (ACT-04, `categories.keep_overspending`, owner-only, never access token, expense categories only): deficit carries, Σ Available unchanged, still counted in `overspent` and listed as `kept`.
- Hold for next month (ACT-03): `PUT /budget/:month/hold`, `setHold` in `services/budgetHolds.ts`, table `budget_holds` (one row per month), owner only; not an assignment; subtracts from RTA in its month and earlier; cannot be assigned while held; can only be raised by what is ready to assign now after later assignments. Not built: Actual's automatic hold.
- Month views: current/later months deduct every positive later-month assignment; past month shows what it closed with (`laterDeduction`). Assignment guard `fundedWrite` (`budgetMoves.ts`) checks every affected month; no write may deepen a shortfall; reductions always allowed; missing rates block any write that takes money; overspending is the one exception.
- Linked envelopes (owner-requested 9 Nov 2026): `categories.linked_account_id` (Settings > Categories > Edit > Follows the account) mirrors an account: `Available = carry + budgeted + transferred + activity` = account balance (`mirrorSteps`, `currentTransferred`, `accountBalanceAt`). `refuseLinked` (`budgetMoves.ts`) refuses assignments and Move money for a linked envelope in every `fundedWrite` writer and `fundingPlan.addAssigned`; auto-assign, Fund targets, payday rules skip it. One envelope per account (unique index); expense envelopes only (not income/card payment); open checking, savings or cash accounts in the personal budget only; `ON DELETE SET NULL`; read-only tokens cannot set the link (`categoryManageAllows` in `auth/assistantPolicy.ts`).
- Own Ready-to-Assign pools (owner-requested 7 Nov 2026): `accounts.assign_pool`; turning on earmarks categories of active recurring bills paid from it (`categories.pool_account_id`); "Edit category > Ready to assign from"; code `services/assignPools.ts`; each pool has `resources`, `envelopes`, `readyToAssign`; main `unassigned`, `unassignedBeforeLater`, `toBeBudgeted` exclude pool RTA (property test in `readyToAssign.test.ts`); guard refuses a write that would take a pool below zero; later-month assignments and holds count against the main figure; `budget_summary` (MCP) includes `pools`. (Doc states no rule for an account that is both a pool and a linked envelope; see conflicts report.)
- Resources: dated balances of personal on-budget checking, savings, cash, credit, line-of-credit accounts; household pools and off-budget contribute nothing; closed accounts count until zero; internal transfers create no resources. Interim net-debt model for unreviewed cards.
- Dates: `todayIso` server local date; payday uses plan's time zone; historical summary uses earlier of month end and today; response includes `asOf`. Missing rates make assessment incomplete and block funding and moves; foreign account revaluation lands in Ready to Assign.
- Planned assigning (one path, audit F-13): `services/fundingPlan.ts` `planFunding`, `applyFundingPlan` (rebuilds plan inside funded write; 409 if different), `addAssigned` single write; preview format `rows` (`proposed`,`shortfall`), `total`, `shortfall`, `complete`, `revision`. Desktop Assign menu `components/budget/AssignMenu.tsx`. Auto-assign (`services/autoAssign.ts`) strategies: cover overspending, underfunded, assigned last month, spent last month, average spent over 3/6/12 months, `zero`; `mode` add|replace; `categoryIds` scope (BUD-07, `useScopedPlan`, `FundingRows`).
- Typing assignments (BUD-05): `readAmountExpression` (`client/src/utils/amountExpression.ts`) supports `+ - * /` (and x, division sign), brackets, BigInt exact fractions, round half away from zero once, no `eval`, never relative; leading `*` or `/` refused; negative assignments allowed on both desktop and phone (`assignmentToInput`); desktop keys Enter/Escape/Down/Tab/Up (rows from `tr[data-budget-row]`). Not built: one amount to several selected envelopes.
- Inspector and notes (BUD-10): `BudgetInspector.tsx`; `budget_month_notes` and `category_notes`, migration 0077, backup format 29; `services/budgetNotes.ts` single writer; `PUT /budget/:month/note`, `PUT /budget/category/:categoryId/note` (`{note}`, max 2,000 chars, trimmed, empty removes), `GET /budget/:month/note`; no `budget_revision` trigger; owner only (token may read, never write). Older `budget_months.notes` column unread. `NoteField.tsx`.
- Moves: Move money (desktop and phone) between two distinct expense categories; preview then apply; assignment pair and durable operation in one DB transaction; future-month moves not enabled; BUD-06 row buttons prefill `useMoveRequest`/`store/moveRequestStore.ts`; `READY_TO_ASSIGN` sentinel (`budgetMoves.ts`, mirrored `MoneyMoves.tsx`) accepted as destination only (stored as `destination_id`, no migration; goal retire-and-move refuses it in `goalLifecycle.ts`); `sourceTarget`/`destinationTarget` via `targetEffect`; history latest 100; undo restores both only if no relevant change; portable backup version 7 retains operations; currency decimal changes blocked while move history exists.
- Budget start: `budget_settings.budget_start_month` (null = all history); `budget_start_day` (migration 0063); `startBudgetIfNew` called by `POST /up/map-accounts`; `PUT /budget/start` with `day:null` to count the whole month; `sinceBudgetStart` in `services/balances.ts`. Reports/register/runway ignore the start.
- Balance checks: `accountIssues` nonempty => `available` zero, `resolved` false, new manual/payday/card reserve funding refused; closing an account requires zero register balance in the same transaction; reconciliation: one dated snapshot, revision and register-balance check reject stale saves, correction and reconciliation commit in one DB transaction; only owner session may use writing routes; income schedules never auto-create entries in closed accounts or duplicate a bank receipt. Expected bill details popover (`ExpectedNote`), links `/recurring?schedule=<id>`.
- Ledger cache keyed on `fundingRevision()` (today's date + revision bumped by SQLite triggers on writes to transactions, accounts, assignments, categories and groups, rates, budget settings, card funding, household tables); a new input needs a trigger (migration) or stay out of engine; `budgetEngine.test.ts` holds it to previous per-month engine.

## Files (document library)
- source: docs/FILES.md
- type: schema
- content: Status built (0.2.0-up.79). Text search: `fileText.ts`; photos read only by owner-chosen model when receipt reading is on (`text_status`: null|pending|read|none|failed). Share target: `client/public/manifest.webmanifest`, `public/sw.js` `receiveShare`, cache `flybudget-shared`, max 20 files, route `/share-target` then `/files?shared=N`.
- API: `GET /files`, `POST /files?fileName=&linkKind=&linkId=&tagIds=`, `GET|PATCH /files/:id`, `POST /files/:id/links`, `DELETE /files/:id/links/:kind/:targetId`, `POST /files/:id/receipt`, `POST /files/:id/text`, `DELETE /files/:id`, `GET /files/:id/file`, `GET /files/counts`, `GET|PUT /files/storage`, `GET /files/export`.
- Not built: email inbox, files for read-only assistant, video thumbnails, OCR/HEIC text.
- Tests named: `server/src/routes/files.test.ts`, `client/src/utils/transactionFilters.test.ts`, `e2e/tests/files.spec.ts`.

## Savings forecasts (cash runway, scenarios; phase 5)
- source: docs/FORECASTS.md
- type: api-contract
- content: Implementation `0.2.0-up.13`; Forecast opens on the long-term forecast, Cash runway is the second tab. Forecast never creates transactions, schedules, goal values or assignments. Starting cash = open, on-budget, personal cash and card accounts (checking, savings, cash, credit card, line of credit); excludes household pool, off-budget, loans, investments; unreconciled generated salary excluded. Income from active payday plans or pending scheduled income, never both.
